# 处理过程与最终结果同一排版

日期：2026-10-04 · 来源：用户「处理过程的消息能不能和最终消息保持一致？现在格式还是老格式，只有最终消息是新的，而且群里自动触发的只有处理中这三个字，只有inline有格式，能不能统一一下啊」

> ## ⚠️ 回退与恢复的经过（重要）
>
> 这个改动**上线后被我自己回退过**，又恢复了。原因是：
>
> - 排查"R18 自动遮罩没工作"时，我的探针用 `getattr(block, "spoiler")` 读打码标记
>   —— **字段名是错的**（正确的是 **`has_spoiler`**），于是读到 `None`，
>   据此**误判"处理过程中的 markdown 富文本弄坏了遮罩"**，就把这个改动 revert 了。
> - 后来发现真正的问题是**缓存路径从来不打码**（另一个 bug），而遮罩**一直是好的**。
>
> **恢复前补了前提验证**（这才是当初该做的）：
>
> ```
> ① 先发 markdown 富文本 (模拟处理过程):  RichBlockParagraph
> ② 再编辑成 blocks (模拟结果):           RichBlockPhoto has_spoiler=True   ← 不冲突
> ```
>
> ⇒ **处理过程用 markdown 富文本，不会影响之后编辑成 blocks 打码。** 回退理由不成立。
>
> **教训**：用探针断言字段之前先核实字段名 —— 一个猜错的字段名会造出"功能坏了"的假象，
> 并把自己引向错误的回退。

## 问题

处理过程是**纯文本小字**（`format_label` → `<b>▎解 析 中...</b>`），最终结果是**富文本** ——
结果一到就整篇跳格式。

| 入口 | 处理过程 | 观感 |
| --- | --- | --- |
| 私聊/群自动 | `msg.reply("▎解 析 中...")` | 只有一片小字 |
| inline | `edit_inline_text(原 caption + 进度)` | 看起来"有格式"，其实只是把用户消息的原文带上了 |

## 目标与做法

> ⚠️ **2026-10-09 更新：这里的「解析中 → 骨架」首帧已取消** —— 解析阶段不再发消息，
> 第一条消息直接是解析完的文字排版（页脚仍带「下载中」）。
> 见 `2026-10-09-first-frame-without-parsing-stage.md`；下面这段描述的是当时的形态。

**从第一秒到最后都是同一种排版**，内容逐步充实：

```
解析中   →  骨架: 进度行(正文) + 页脚(来源链接)
下载中   →  完整排版: 标题/作者/正文/标签/引用块 + 页脚(进度 · 来源)   ← 只差媒体
处理中   →  同上
上传中   →  同上
结果     →  同上 + 媒体
```

- **进度文案放页脚第一段**（就是最终结果里"时间 · 统计"那个位置）→ **主体位置完全不动**，
  只有页脚那一段在变。这是"不跳版"的关键。
- 骨架与完整排版的**结构一致**（正文 + `---` + 页脚），结果落地时不跳。

## 接口变化

`StatusReporter` 从一个 `report(text)` 拆成三个 —— 因为"阶段切换"和"进度刷新"的需求不同：

| 方法 | 何时 | 是否节流 |
| --- | --- | --- |
| `report(text)` | 阶段切换（还没有解析结果）→ 骨架 | **否**（必发） |
| `report_progress(text)` | 进度刷新（下载百分比） | **是** |
| `report_result(parse_result, text)` | **已有**解析结果 → 完整排版 | 否（必发） |

**为什么必须有"不节流"的那条**：`PipelineProgressCallback` 按下载进度密集调用，
富文本编辑比纯文本重得多（重渲染整篇 + 更大 payload），不节流会被 Telegram 限流；
但"解析中 → 下载中"这种**快速阶段切换**如果被节流吞掉，用户就看不到阶段推进了。
所以节流只作用于**进度刷新**。

`_MIN_PROGRESS_INTERVAL = 1.5s`（`plugins/parse/reporters.py`）。

## ⚠️ footer 里只有 HTML 标签解析（`**` 会字面显示）

阶段标签放页脚，而**页脚块只解析 HTML 标签** —— 与"footer 里 markdown 链接不解析"
同一个坑。真机四组对照：

| 位置 | 写法 | 结果 |
| --- | --- | --- |
| **footer** | `**▎…**`（markdown） | ✗ 字面显示，用户看到多余的 `**` |
| **footer** | `<b>▎…</b>` | ✓ `RichTextBold` |
| 正文 | `**▎…**` | ✓ `RichTextBold` |
| 正文 | `<b>▎…</b>` | ✓ `RichTextBold` |

**这个来回值得记**：我曾为了"迁就 blocks 路径不认 `<b>`"把标签改成 `**` ——
**方向搞反了**（用户当场指出"第一次改的时候是正常的"）。
正确做法是**让 blocks 的 `parse_inline` 认 `<b>`/`<i>`**，而不是改坏 markdown 路径。
现在两处都对：footer 用 `<b>`，`parse_inline` 也认 `<b>`/`<i>`。

## 三个实现要点（都是踩过的）

1. **进度刷新必须复用最近的结果**：下载阶段的进度刷新若走骨架渲染，每刷一次就跳一次版。
   reporter 记住最后一次 `report_result` 给的 `parse_result`（`self._parse_result`）。
2. **判重不能用 `msg.text`**：富文本消息的 `text` 是空的，用它等于每次都编辑。
   改成自己记 `_last_markdown`。
3. **打码必须贯穿处理过程**：`spoiler_tag` 传进 reporter。否则"下载中"那几秒
   就把该藏的内容露出来了（真机验证：② 下载中 已经带 ⚠️ #nsfw 折叠）。

## 渲染入口

`plugins/helpers.py` 新增 `build_progress_markdown(parse_result | None, *, progress, ...)`：

- 有结果 → `build_rich_markdown(..., progress=..., 无媒体占位符)`
- 无结果 → 骨架（进度 + 页脚来源），来源由 `raw_url` 推平台

`build_rich_markdown` 新增 `progress` 参数，插在 `footer_parts` **最前面**。

## 边界

- **raw / zip**：最终是**文件消息**（Telegram 不允许文本编辑成文件），本质上无法与处理过程
  一致。处理过程仍按富文本做（各入口观感统一），这类路径的**结果形态**例外。
- **缓存直发**：一次发完、不经过处理过程，不受影响。
- **inline / guest**：与私聊/群同一套 reporter（`InlineStatusReporter`），走
  `edit_inline_rich_message`；顺带第一次进度更新就把结果项上的键盘摘掉了。
