# 引用块的角色：位置推断 → 平台显式声明

日期：2026-10-07

## 问题

渲染层靠**位置**判断引用块的角色，并用同一套位置约定切分媒体：

- 引用块在正文**开头** → 「被回复」卡片，媒体走 `reply_media_count`
- 引用块在正文**末尾** → 「被引用」卡片，媒体走 `quoted_media_count`

于是**正文里多一行、少一行都能把归位搅乱**。同一件事在 bgm 上踩到两次：

1. **多一行**：归属行（「小组/条目名 » 讨论」）插在引用块前面 ⇒ 引用块落到末尾 ⇒
   本层的图被插到它**前面**贴住（用户报「图片和引用贴一起了」）。
2. **少一行**：把归属行挪走后，**没有正文**的纯图楼层里引用块是该产物的唯一一块 ⇒
   `split_quote_blocks` 从末尾往上扫，把它判成"末尾块" ⇒ 图同样排到它前面
   （真机实测：`图 → 引用块`）。

用户的判断：「你写的架构有问题？怎么还有顺序的？闻所未闻」—— 对，角色该显式声明。

**佐证**：三个平台（twitter / threads / bilibili）的块位置与媒体通道**恰好一致**，
所以一直没暴露；linux.do 与 bgm 不一致 —— 它们靠一张"两个块互相兜底"的表撑着。
那张表不是设计，是打给位置推断的补丁。

## 现在

`ParseResult.quote_roles`：平台按块在正文中**出现的顺序**声明角色，取值就是两个媒体通道名。

| 角色 | 卡片渲染在 | 媒体取 |
| --- | --- | --- |
| `reply` | 正文**之前** | `reply_media_count` 段 |
| `quoted` | 正文**之后** | `quoted_media_count` 段 |

**角色同时决定"哪一侧"与"哪一段媒体"** —— 块写在正文哪里都不影响结果。

各平台现状：

| 平台 | 块位置 | 声明 | 媒体 |
| --- | --- | --- | --- |
| twitter | reply 在前、quoted 在后 | `["reply","quoted"]` | 两段各用各的 |
| threads | 被回复帖在前 | `["reply"]` | `reply_media_count` |
| linux.do | 上下文层在前 | `["reply"]` | `reply_media_count` |
| bilibili | 转发块在后 | `["quoted"]` | `quoted_media_count` |
| bgm | 上下文层在前 | `["reply"]` | `reply_media_count` |

（linux.do 与 bgm 原本把上下文媒体算在 `quoted_media_count` —— 块在前、媒体在后段，
这正是"位置与通道不一致"的来源；现在两者对齐到 `reply`。）

## 顺带：归属行进元信息区

归属行不再拼进正文，改由 `ParseResult.origin_line` 交给渲染层，放在
**标题与作者行之间**（用户要求的位置）。它本来就是"这是什么"而不是"说了什么"。

## 回退

`quote_roles` 为空（老缓存 / 未改的平台）时走原来的位置推断 —— 那条路径**逐字保留**，
有测试断言"形态一致时声明与不声明产物完全相同"。

## 验证

真机四种形态（生产容器、完整流水线）：

| 场景 | 渲染顺序 |
| --- | --- |
| bgm 纯图楼中楼 | 标题 → 归属行 → 作者行 → **引用块 → 图** |
| bgm 条目讨论楼层 | 标题 → 归属行 → 作者行 → 引用块 → 正文 |
| twitter 引用带图 | 作者行 → 正文 → 图 → 引用块 → **图(块内)** |
| linux.do 楼层 | 标题 → 作者行 → 引用块 → **图(块内)** → 正文 |

测试：`lib/test/test_quote_roles.py`（契约 + 缓存 round-trip）、
`test/test_quote_roles_layout.py`（角色决定顺序与媒体 + 回退路径）、
`test/test_origin_line.py`（归属行位置）、各平台测试里的 roles 断言。

## 教训

**用位置当身份标识，等于把语义绑在排版上** —— 排版一动，语义就漂。
显式声明（哪怕只多一个字段）比事后补兜底表可靠：兜底表只覆盖当时想到的形态，
而位置组合是无穷的。判断标准：如果一处逻辑在回答"这个东西**是什么**"，
它就不该依赖"它**排在哪**"。
